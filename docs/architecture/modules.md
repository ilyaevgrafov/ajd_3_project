# Архитектура приложения

**Статус:** планируемая архитектура  
**Подход:** модульный монолит на Spring Boot с использованием Spring Modulith

## 1. Общая организация

Приложение представляет собой модульный монолит: единый исполняемый Spring Boot-сервис, единый Maven-проект и общую базу данных PostgreSQL. Код разделяется на модули по предметной ответственности. Каждый бизнес-модуль управляет собственной логикой и принадлежащими ему данными.

| Модуль | Категория | Ответственность | Таблицы в зоне ответственности |
| --- | --- | --- | --- |
| `identity` | Бизнес-модуль | Учётные записи, аутентификация, профиль и безопасность | `users`, `account_tokens` |
| `spaces` | Бизнес-модуль | Пространства, участники, роли и приглашения | `spaces`, `space_memberships`, `space_invitations` |
| `tasks` | Бизнес-модуль | Задачи, назначения, статусы, теги и история изменений | `tasks`, `task_statuses`, `space_tags`, `task_tags`, `task_changes` |
| `analytics` | Бизнес-модуль | Аналитические показатели пространств и участников | На начальном этапе собственные таблицы не требуются |
| `workflows` | Координационный модуль | Сценарии, затрагивающие несколько бизнес-модулей | Не владеет предметными таблицами |
| `infrastructure` | Технический модуль | Общая конфигурация и инфраструктурные компоненты приложения | Не владеет предметными таблицами |

`identity`, `spaces` и `tasks` реализуются на начальных этапах. `analytics` и необходимые компоненты `workflows` и `infrastructure` добавляются по мере появления соответствующих сценариев. Все шесть модулей включены в целевую архитектуру.

## 2. Структура исходного кода

Корневой Java-пакет: `io.github.vijteam.didgeridoo`.

```text
src/main/java/io/github/vijteam/didgeridoo/
├── DidgeridooApplication.java
├── identity/
│   ├── UserDirectory.java
│   └── internal/
│       ├── controller/
│       ├── service/
│       ├── repository/
│       ├── model/
│       └── dto/
├── spaces/
│   ├── SpaceAccess.java
│   └── internal/
│       ├── controller/
│       ├── service/
│       ├── repository/
│       ├── model/
│       └── dto/
├── tasks/
│   ├── TaskQueries.java
│   └── internal/
│       ├── controller/
│       ├── service/
│       ├── repository/
│       ├── model/
│       └── dto/
├── analytics/
│   └── internal/
│       ├── controller/
│       ├── service/
│       └── dto/
├── workflows/
│   └── internal/
│       ├── controller/
│       └── service/
└── infrastructure/
    ├── security/
    ├── exception/
    └── config/
```

Названия публичных интерфейсов приведены как ориентиры; конкретные контракты определяются при реализации сценариев. Пакеты и классы создаются по мере необходимости.

| Область | Назначение |
| --- | --- |
| Корень бизнес-модуля | Публичный Java API: операции и типы данных, доступные другим модулям |
| `internal/controller` | REST-эндпоинты, обработка запросов и формирование ответов |
| `internal/service` | Бизнес-операции, проверка полномочий и транзакционные границы внутри модуля |
| `internal/model` | JPA-сущности и внутренние типы предметной области |
| `internal/repository` | Доступ к данным через Spring Data JPA |
| `internal/dto` | Модели HTTP-запросов и ответов |
| `workflows/internal/service` | Координация межмодульных бизнес-операций |
| `workflows/internal/controller` | Точки входа для межмодульных сценариев, требующих отдельного REST-эндпоинта |
| `infrastructure/security` | Конфигурация Spring Security и общие механизмы HTTP-безопасности |
| `infrastructure/exception` | Единый формат ошибок и обработка исключений HTTP API |
| `infrastructure/config` | Общая конфигурация Spring Boot и используемых библиотек |

Внутренняя структура модулей может уточняться по функциональным областям. Пакет `internal` отделяет реализацию от публичного API модуля. Бизнес-правила размещаются в предметных модулях; `infrastructure` содержит общесистемные технические компоненты.

## 3. Обязанности модулей

### 3.1. `identity`

**Владеет:** жизненным циклом учётной записи и персональными данными пользователя.

Функции:

- Регистрация и аутентификация, управление сеансами.
- Подтверждение электронной почты и восстановление доступа.
- Редактирование профиля и аватара.
- Изменение пароля и электронной почты.
- Проверка учётных данных при удалении аккаунта.
- Предоставление другим модулям необходимых сведений о пользователях.

Публичный API предоставляет операции проверки существования пользователя и получения согласованного набора пользовательских данных. Реализация аутентификации интегрируется со Spring Security. Общая конфигурация безопасности находится в `infrastructure/security`; сведения о членстве в пространствах принадлежат `spaces`.

### 3.2. `spaces`

**Владеет:** жизненным циклом пространств, членством и ролями пользователей.

Функции:

- Создание, переименование, поиск и удаление пространств.
- Ведение состава пространства и ролей `GUEST`, `MEMBER`, `OWNER`.
- Создание, принятие, отклонение и отмена приглашений.
- Изменение ролей, исключение и добровольный выход.
- Передача владения по правилам [функциональных требований](../requirements.md).
- Проверка членства, роли и допустимости назначения пользователя исполнителем.

Публичный API предоставляет сведения о членстве, операции проверки полномочий и изменения состава пространства. Управление статусами и тегами задач относится к `tasks`.

### 3.3. `tasks`

**Владеет:** жизненным циклом задач и связанными с ними правилами.

Функции:

- Создание, чтение, редактирование и удаление задач.
- Управление исполнителем и источником назначения (`DIRECT`, `SELF_CLAIM`).
- Самостоятельное взятие и освобождение свободных задач.
- Применение разрешения `assigneeCanEdit` независимо от способа назначения.
- Управление статусами и тегами пространства.
- Поиск, сортировка и фильтрация задач.
- Подготовка данных для бэклога, канбана, календаря и общего представления задач.
- Запись и предоставление истории изменений.

Публичный API предоставляет операции, необходимые другим модулям, включая обработку прекращения участия пользователя и удаление связанных данных пространства. Для проверки членства и роли используется публичный API `spaces`; правила, зависящие от создателя, исполнителя и состояния задачи, применяются внутри `tasks`.

### 3.4. `analytics`

**Владеет:** вычислением и предоставлением аналитических показателей.

Функции:

- Расчёт общей статистики пространства.
- Расчёт индивидуальных показателей участников.
- Применение временных интервалов к показателям, определённым в функциональных требованиях.
- Проверка доступа к аналитике через публичный API `spaces`.

Модуль получает необходимые данные через публичные запросы и проекции `tasks` и `spaces`. Показатели и правила их расчёта определяются в [функциональных требованиях](../requirements.md).

### 3.5. `workflows`

**Владеет:** координацией бизнес-операций, изменяющих состояние нескольких модулей.

Основные сценарии:

- Создание пространства с обязательными начальными статусами.
- Выход и исключение пользователя из пространства.
- Изменение роли пользователя на `GUEST`.
- Удаление учётной записи с обработкой членства, задач и передачи владения.
- Удаление пространства со связанными данными.

Координирующие сервисы вызывают публичные API бизнес-модулей и определяют общую транзакционную границу. Операции, затрагивающие только один модуль, выполняются его собственными сервисами.

### 3.6. `infrastructure`

**Владеет:** техническими компонентами, общими для приложения.

- `security` — конфигурация Spring Security, цепочки фильтров и общие механизмы аутентифицированного доступа.
- `exception` — централизованная обработка HTTP-ошибок и формат ответа об ошибке.
- `config` — общие настройки приложения и интеграций с техническими библиотеками.

Предметные проверки разрешений остаются в бизнес-модулях. `infrastructure` предоставляет общие технические механизмы и не управляет предметными сущностями.

## 4. Правила взаимодействия

### 4.1. Направления зависимостей

Допустимые направления основных зависимостей:

```text
workflows ─────► identity, spaces, tasks
analytics ─────► spaces, tasks
      tasks ──► spaces ──► identity
         └────► identity (при необходимости)
```

`infrastructure` предоставляет общие технические компоненты. Его включение в интеграционные тесты модулей может настраиваться средствами Spring Modulith как shared module.

- `spaces` обращается к `identity` для проверки пользователей и получения необходимых сведений.
- `tasks` обращается к `spaces` для проверки участия, ролей и допустимости исполнителей.
- `tasks` может обращаться к `identity` для получения пользовательских данных при формировании ответов.
- `analytics` использует публичные запросы `tasks` и `spaces`.
- `workflows` обращается к публичным API модулей для выполнения согласованных операций.

Вызовы между модулями выполняются через публичные контракты корневого пакета модуля либо явно опубликованные именованные интерфейсы Spring Modulith. Внутренние классы, репозитории и JPA-сущности доступны только внутри модуля-владельца.

Граф зависимостей должен оставаться ациклическим. Координационные сценарии реализуются в `workflows`, сохраняя это ограничение.

### 4.2. Контракты

Публичный контракт определяет операции, параметры, результаты и ошибки, значимые для потребителей. Контракты расширяются по мере реализации сценариев.

При параллельной разработке допускается локальный интерфейс для ещё не предоставленной внешней операции. После появления публичного API модуля-владельца локальная зависимость связывается с ним через адаптер либо заменяется прямым вызовом. В интегрируемой функциональности используются согласованные реализации.

### 4.3. Данные между модулями

Публичные контракты используют идентификаторы, примитивные значения и специально определённые публичные типы данных. Внутренние JPA-сущности не передаются через границы модулей.

JPA-связи допустимы между сущностями одного модуля. Межмодульные ссылки представляются идентификаторами; целостность отношений обеспечивает PostgreSQL, а операции с данными выполняются через публичные API модулей-владельцев.

Например, `tasks` хранит идентификаторы пространства, создателя и исполнителя задачи и обращается к `spaces` для проверки актуальных ролей.

## 5. Межмодульные бизнес-операции

Транзакционная граница межмодульного сценария устанавливается на уровне координирующего сервиса `workflows`. Операции, требующие атомарности, выполняются в единой транзакции PostgreSQL.

| Сценарий | Модули | Атомарная операция |
| --- | --- | --- |
| Создание пространства | `spaces`, `tasks` | Создание пространства, назначения владельца и начального/конечного статусов |
| Выход или исключение пользователя | `spaces`, `tasks` | Освобождение назначенных задач и прекращение участия |
| Перевод пользователя в `GUEST` | `spaces`, `tasks` | Снятие назначений и изменение роли |
| Удаление учётной записи | `identity`, `spaces`, `tasks` | Обработка задач, членства и передачи владения с последующим удалением аккаунта |
| Удаление пространства | `spaces`, `tasks` | Удаление пространства и связанных данных с соблюдением внешних ключей |

Правила добровольного выхода и удаления учётной записи определяются отдельно в [функциональных требованиях](../requirements.md). При удалении аккаунта передача владения производится автоматически, включая предусмотренный требованиями выбор из оставшихся гостей при отсутствии обычных участников.

Создание задачи и самостоятельное назначение исполнителя выполняются с проверкой актуальных полномочий. Конкурентные попытки назначить одну свободную задачу обрабатываются атомарным обновлением или блокировкой на уровне PostgreSQL.

## 6. Контроль архитектуры и тестирование

Spring Modulith используется для контроля модульных границ. Структура зависимостей проверяется автоматизированным тестом с вызовом `ApplicationModules.verify()`.

Предусматриваются:

- Модульные тесты бизнес-правил с изолированными зависимостями.
- Интеграционные тесты репозиториев и ограничений PostgreSQL с использованием Testcontainers.
- Интеграционные тесты межмодульных сценариев с реальными реализациями.
- Проверки конкурентных операций над задачами и членством.

`infrastructure` при необходимости объявляется общим модулем через `@Modulithic(sharedModules = "infrastructure")` для включения в модульные интеграционные тесты. Это не отменяет правил доступа к внутренним пакетам.

## 7. Развитие архитектуры

Модули и их публичные API реализуются последовательно в соответствии с [планом разработки](../roadmap.md). Новые модули выделяются при появлении самостоятельной предметной ответственности; изменения границ и зависимостей отражаются в настоящем документе.
