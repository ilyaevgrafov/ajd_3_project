# Модель данных

**СУБД:** PostgreSQL  
**Статус:** проектируемая схема  
**Исходная модель:** [database.dbml](database.dbml) · [ER-диаграмма](database.png)  
**Связанные документы:** [Функциональные требования](../../requirements.md) · [План реализации](../../roadmap.md)

## 1. Назначение

Модель данных обеспечивает хранение учётных записей, пространств задач, участия пользователей, приглашений, задач, настраиваемых статусов и тегов, а также истории изменений задач.

Логические области модели:

| Область | Таблицы |
| --- | --- |
| Учётные записи | `users`, `account_tokens` |
| Пространства и доступ | `spaces`, `space_memberships`, `space_invitations` |
| Конфигурация пространства | `task_statuses`, `space_tags` |
| Управление задачами | `tasks`, `task_tags` |
| История изменений | `task_changes` |

Бэклог, канбан, календарь и аналитические показатели формируются на основе данных этих таблиц.

## 2. Структура данных

### 2.1. `users`

Учётные записи пользователей.

| Поле | Назначение |
| --- | --- |
| `id` | Идентификатор пользователя |
| `username` | Уникальное имя пользователя |
| `display_name` | Отображаемое имя |
| `email` | Уникальный адрес электронной почты |
| `password_hash` | Данные аутентификации |
| `email_verified_at` | Время подтверждения адреса электронной почты |
| `avatar_storage_key` | Ключ объекта аватара в файловом хранилище |
| `created_at`, `updated_at` | Временные метки |

Для `username` и `email` используется тип `citext` с уникальными ограничениями.

### 2.2. `account_tokens`

Одноразовые подтверждения операций с учётной записью.

| Поле | Назначение |
| --- | --- |
| `user_id` | Пользователь |
| `kind` | `VERIFY_EMAIL`, `RESET_PASSWORD`, `CHANGE_EMAIL`, `CHANGE_PASSWORD` |
| `token_hash` | Идентификатор подтверждения |
| `proposed_email` | Новый адрес для операции `CHANGE_EMAIL` |
| `expires_at` | Срок действия |
| `consumed_at` | Время использования |
| `created_at` | Время создания |

Успешное подтверждение операции фиксирует `consumed_at` в одной транзакции с изменением учётной записи.

### 2.3. `spaces`

Пространства задач. Таблица содержит идентификатор, название и временные метки.

Создание пространства сопровождается созданием членства с ролью `OWNER`, начального статуса и конечного статуса в одной транзакции.

### 2.4. `space_memberships`

Связь пользователя с пространством и его текущая роль.

| Поле | Назначение |
| --- | --- |
| `space_id` | Пространство |
| `user_id` | Пользователь |
| `role` | `GUEST`, `MEMBER`, `OWNER` |
| `joined_at` | Время вступления |

Первичный ключ — `(space_id, user_id)`. Каждая запись задаёт единственную текущую роль пользователя в пространстве. Значение `joined_at` участвует в автоматическом определении преемника владельца.

### 2.5. `space_invitations`

Приглашения зарегистрированных пользователей в пространство.

| Поле | Назначение |
| --- | --- |
| `space_id` | Пространство |
| `invited_user_id` | Получатель приглашения |
| `invited_by_user_id` | Инициатор приглашения |
| `proposed_role` | Роль при вступлении |
| `state` | `PENDING`, `ACCEPTED`, `DECLINED`, `CANCELLED` |
| `created_at`, `resolved_at` | Время создания и завершения |

Одновременно допускается одно приглашение со статусом `PENDING` для пары `(space_id, invited_user_id)`. Принятие приглашения создаёт запись в `space_memberships` и переводит приглашение в `ACCEPTED` в одной транзакции.

### 2.6. `task_statuses`

Упорядоченные статусы задач конкретного пространства.

| Поле | Назначение |
| --- | --- |
| `space_id` | Пространство |
| `name` | Название статуса |
| `kind` | `INITIAL`, `INTERMEDIATE`, `FINAL` |
| `position` | Позиция в порядке отображения |
| `created_at` | Время создания |

Для каждого пространства определены ровно один `INITIAL` и один `FINAL`. Начальный статус занимает минимальную позицию, конечный — максимальную. Порядок остальных статусов определяется `position`.

Начальный и конечный статусы сохраняют свой тип и крайнее положение при редактировании. При удалении промежуточного статуса связанные задачи переводятся в начальный статус.

Уникальные ключи: `(space_id, id)` и `(space_id, position)`.

### 2.7. `space_tags`

Справочник тегов пространства. Каждая запись содержит `space_id`, `name` и `created_at`.

Уникальность названия обеспечивается в пределах пространства ключом `(space_id, name)`. При удалении тега удаляются соответствующие связи в `task_tags`.

### 2.8. `tasks`

Основная сущность управления задачами.

| Поле | Назначение |
| --- | --- |
| `id`, `space_id` | Идентификатор задачи и принадлежность пространству |
| `creator_user_id` | Создатель задачи |
| `assignee_user_id` | Текущий исполнитель |
| `status_id` | Статус задачи |
| `title`, `description` | Содержание задачи |
| `deadline_at` | Срок выполнения |
| `priority` | `LOW`, `MEDIUM`, `HIGH`, `URGENT` |
| `assignee_can_edit` | Разрешение исполнителю редактировать содержание задачи |
| `assignment_source` | `DIRECT`, `SELF_CLAIM` |
| `created_at`, `updated_at` | Временные метки |

Задача принадлежит одному пространству. Значения `status_id`, `assignee_user_id` и связанные теги определяются в рамках этого пространства.

При отсутствии исполнителя `assignee_user_id` и `assignment_source` принимают `NULL`. При наличии исполнителя источник назначения обязателен.

**Семантика источника назначения:**

- `DIRECT` — назначение создателем самому себе или владельцем пространства.
- `SELF_CLAIM` — участник самостоятельно взял свободную задачу и вправе освободить её без участия владельца пространства.

Исполнитель вправе изменять статус задачи и редактировать её содержание при `assignee_can_edit = true` независимо от источника назначения. Полномочия создателя задачи и владельца пространства применяются независимо от источника назначения.

### 2.9. `task_tags`

Связь задач с тегами по модели «многие ко многим».

Первичный ключ — `(task_id, tag_id)`. Составные внешние ключи `(space_id, task_id)` и `(space_id, tag_id)` обеспечивают принадлежность задачи и тега одному пространству.

### 2.10. `task_changes`

История создания и изменения задач.

| Поле | Назначение |
| --- | --- |
| `task_id` | Задача |
| `actor_user_id` | Пользователь, выполнивший операцию |
| `kind` | `CREATED`, `UPDATED` |
| `changed_fields` | Набор изменений полей в формате `jsonb` |
| `created_at` | Время события |

Изменение поля представляется парой исходного и нового значений:

```json
{
  "priority": {"from": "LOW", "to": "HIGH"},
  "status": {"from": "Todo", "to": "In progress"}
}
```

Изменение задачи и запись истории выполняются в одной транзакции. История сохраняется при выходе создателя или исполнителя из пространства. При удалении учётной записи ссылка `actor_user_id` принимает `NULL`.

## 3. Связи и ссылочная целостность

| Родительская сущность | Зависимая сущность | Правило |
| --- | --- | --- |
| `users` | `account_tokens` | `ON DELETE CASCADE` |
| `users` | `space_memberships` | `ON DELETE CASCADE` |
| `users` | `space_invitations.invited_user_id` | `ON DELETE CASCADE` |
| `users` | `space_invitations.invited_by_user_id` | `ON DELETE SET NULL` |
| `users` | `tasks.creator_user_id` | `ON DELETE SET NULL` |
| `users` | `task_changes.actor_user_id` | `ON DELETE SET NULL` |
| `spaces` | `space_memberships`, `space_invitations`, `task_statuses`, `space_tags`, `tasks` | `ON DELETE CASCADE` |
| `tasks` | `task_tags`, `task_changes` | `ON DELETE CASCADE` |
| `space_tags` | `task_tags` | `ON DELETE CASCADE` |
| `space_memberships` | `tasks` (исполнитель) | `NO ACTION` |
| `task_statuses` | `tasks` | `NO ACTION` |

Для исполнителя предусмотрены ссылки `tasks.assignee_user_id → users.id` и `(tasks.space_id, tasks.assignee_user_id) → space_memberships(space_id, user_id)`. Перед удалением членства, содержащего активные назначения, исполнитель освобождается в рамках транзакции.

Связь задачи со статусом задаётся составным ключом `(space_id, status_id)`, связь с тегами — составными ключами в `task_tags`.

## 4. Инварианты и механизмы обеспечения

### 4.1. Ограничения PostgreSQL

При создании схемы миграции должны устанавливать:

1. Первичные и внешние ключи, отражённые в `database.dbml`.
2. Уникальность `users.username`, `users.email`, `(space_id, user_id)` для членства, `(space_id, position)` для статусов и `(space_id, name)` для тегов.
3. Согласованность исполнителя и источника назначения через `CHECK` таблицы `tasks`.
4. Непустое название задачи и неотрицательную позицию статуса.
5. Уникальность начального и конечного статуса в пределах пространства.
6. Уникальность ожидающего приглашения для пары «пространство — пользователь».

Для правил 5–6 используются частичные индексы:

```sql
CREATE UNIQUE INDEX uq_initial_status_per_space
    ON task_statuses (space_id)
    WHERE kind = 'INITIAL';

CREATE UNIQUE INDEX uq_final_status_per_space
    ON task_statuses (space_id)
    WHERE kind = 'FINAL';

CREATE UNIQUE INDEX uq_pending_invitation_per_space_user
    ON space_invitations (space_id, invited_user_id)
    WHERE state = 'PENDING';
```

### 4.2. Доменные инварианты

Сервисный слой обеспечивает следующие правила в транзакциях:

| Область | Инвариант |
| --- | --- |
| Владение | Каждое существующее пространство имеет минимум одного `OWNER` |
| Инициализация пространства | Созданы членство владельца, `INITIAL` и `FINAL` |
| Статусы | В пространстве присутствуют ровно один начальный и один конечный статус; крайние статусы фиксированы по положению |
| Исполнитель | Исполнитель является действующим `MEMBER` или `OWNER` данного пространства |
| Роль гостя | Перевод исполнителя в `GUEST` сопровождается освобождением всех его задач |
| Назначение `MEMBER` | Участник назначает только себя при создании своей задачи либо самостоятельно занимает свободную задачу |
| Освобождение задачи | Самостоятельное освобождение допустимо при `assignment_source = SELF_CLAIM` и совпадении текущего пользователя с исполнителем |
| Редактирование исполнителем | Содержание чужой задачи доступно при `assignee_can_edit = true` для обоих способов назначения |
| Статус свободной задачи | Любой `MEMBER` пространства вправе изменить статус свободной задачи |
| Удаление промежуточного статуса | Все затронутые задачи предварительно переводятся в `INITIAL` |
| Прекращение участия | Задачи создателя сохраняются; назначения уходящего пользователя освобождаются |
| Приглашение | Вступление и назначение роли выполняются по принятому приглашению |

Авторизация операций основывается на роли в `space_memberships`, авторстве задачи, текущем исполнителе и атрибутах назначения.

## 5. Транзакционные процессы

### 5.1. Создание пространства

В одной транзакции создаются:

1. `spaces`;
2. членство создателя в `space_memberships` с ролью `OWNER`;
3. статусы `INITIAL` и `FINAL` с крайними позициями.

### 5.2. Принятие приглашения

В транзакции проверяется состояние `PENDING`, создаётся членство с `proposed_role`, устанавливаются `state = ACCEPTED` и `resolved_at`.

### 5.3. Изменение роли и прекращение участия

При переводе пользователя в `GUEST` или прекращении участия освобождаются его назначения: `assignee_user_id = NULL`, `assignment_source = NULL`. Изменения задач записываются в `task_changes`.

Выход последнего владельца обрабатывается следующим образом:

1. При наличии другого `OWNER` пользователь выходит из пространства.
2. При наличии только `MEMBER` выходящий назначает нового владельца либо удаляет пространство.
3. Если после выхода отсутствуют `OWNER` и `MEMBER`, пространство удаляется.

Изменение ролей и проверка количества владельцев выполняются атомарно с блокировкой пространства.

### 5.4. Удаление учётной записи

Обработка пространств удаляемого пользователя выполняется в единой транзакционной операции:

1. Для каждого пространства определяется необходимость передачи владения.
2. При отсутствии другого владельца новый `OWNER` выбирается среди оставшихся `MEMBER` по возрастанию `(joined_at, user_id)`; если `MEMBER` нет, выбор выполняется среди оставшихся `GUEST` по тому же порядку.
3. Пространства без оставшихся пользователей удаляются.
4. В сохраняющихся пространствах освобождаются назначения пользователя и удаляется его членство.
5. Удаляется учётная запись; ссылки создателя задач и автора истории обрабатываются посредством `ON DELETE SET NULL`.

При обработке нескольких пространств блокировки захватываются в согласованном порядке идентификаторов.

### 5.5. Перестановка и удаление статусов

Изменение порядка промежуточных статусов выполняется атомарно с блокировкой соответствующего пространства. Для соблюдения уникальности `(space_id, position)` используются временные позиции либо отложенное уникальное ограничение, настроенное SQL-миграцией.

Удаление промежуточного статуса включает подсчёт затронутых задач, подтверждение операции, их перевод в `INITIAL`, запись изменений и удаление статуса.

### 5.6. Самостоятельное назначение свободной задачи

Операция выполняется условным обновлением строки задачи:

```sql
UPDATE tasks
SET assignee_user_id = :user_id,
    assignment_source = 'SELF_CLAIM',
    updated_at = now()
WHERE id = :task_id
  AND space_id = :space_id
  AND assignee_user_id IS NULL
RETURNING id;
```

Успешное изменение возвращает идентификатор задачи. Проверка полномочий и запись `task_changes` входят в ту же транзакцию.

Для самостоятельного освобождения дополнительно проверяются `assignee_user_id = :user_id` и `assignment_source = 'SELF_CLAIM'`.

### 5.7. Удаление данных

- Удаление тега каскадно удаляет соответствующие строки `task_tags`.
- Удаление задачи каскадно удаляет её теги-связи и историю изменений.
- Удаление пространства каскадно удаляет связанные сущности согласно внешним ключам.
- Удаление используемого промежуточного статуса выполняется после переноса связанных задач.

## 6. Представления и аналитика

Данные `tasks`, `task_statuses` и `task_tags` используются для построения бэклога, канбана, календаря, поиска и фильтров.

Завершённость задачи определяется типом её статуса: `task_statuses.kind = 'FINAL'`. Просроченность определяется наличием прошедшего `deadline_at` и незавершённым статусом.

Общие аналитические показатели формируются агрегирующими запросами по пространству. Индивидуальные показатели рассчитываются по `assignee_user_id` с учётом текущей принадлежности пользователя пространству.

Показатели за выбранный период рассчитываются по правилам, утверждаемым в спецификации аналитики. Для показателей, зависящих от событий, используются записи `task_changes`.

## 7. Требования к реализации

- **Миграции:** Flyway определяет структуру PostgreSQL, ограничения, индексы и расширение `citext`.
- **Транзакции:** операции изменения членства, владения, статусов, назначений и удаления аккаунтов выполняются атомарно.
- **Конкурентный доступ:** применяется блокировка строки пространства для операций, затрагивающих инвариант владения или порядок статусов, и условное обновление строки задачи для самостоятельного назначения.
- **История:** изменение задачи и запись `task_changes` выполняются в одной транзакции.
- **Авторизация:** права проверяются сервером по актуальному состоянию членства и задачи.
- **Время:** значения `timestamptz` хранят абсолютные моменты времени; представление в часовой зоне пользователя формируется на прикладном уровне.
- **Индексация:** индексы DBML используются для связей и фильтров по пространству, исполнителю, статусу, дедлайну и времени создания; специализированные поисковые индексы проектируются по требованиям к поисковым запросам.

## 8. Критерии целостности

Реализация модели должна обеспечивать следующие сценарии:

1. Создание пространства атомарно создаёт владельца и два крайних статуса.
2. Параллельные операции изменения ролей сохраняют минимум одного владельца пространства.
3. Статус и теги задачи принадлежат её пространству.
4. Назначение исполнителя допускает только действующего `MEMBER` или `OWNER`.
5. Параллельное самостоятельное взятие свободной задачи приводит к единственному успешному назначению.
6. Исполнитель может изменять содержание задачи при `assignee_can_edit = true` независимо от способа назначения; самостоятельно взявший задачу пользователь вправе её освободить.
7. Удаление промежуточного статуса переводит связанные задачи в начальный статус.
8. Выход участника и удаление учётной записи сохраняют созданные задачи существующих пространств и освобождают назначения.
9. Удаление последнего владельца приводит к передаче роли либо удалению пространства по установленным правилам.
10. Изменения задач согласованы с записями истории.
